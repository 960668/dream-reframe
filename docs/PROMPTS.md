# 提示词调参手册

这份文档只回答一件事：**想让输出变好，该改哪一行，以及怎么知道改对了。**

---

## 一、控制 AI 生成的全部位置

**文字侧**只有四个地方在影响模型输出，其余文件都是展示层；出图侧另有三处，见第六节。

| # | 位置 | 管什么 | 改动的影响范围 |
|---|---|---|---|
| 1 | `src/prompts.js` → `ANALYZE_SYSTEM` | 文字像不像梦；也是「第一人称 + 不写正脸与完整形象」的源头 | 标题、概括、画面描述、身体感 |
| 2 | `src/prompts.js` → `VISUAL_SYSTEM` | 画面像不像梦；视角与人物写法（含「我」的手／影子／脚步） | 风格锚点、英文提示词 |
| 3 | `src/prompts.js` → `analyzeUserPrompt` / `visualUserPrompt` | 怎么把输入包给模型 | 每次请求的语境 |
| 4 | `src/pipeline.js` 的 `temperature` | 发散程度（解析段 0.85 / 视觉段 0.6） | 全局 |

> 本文档只写了**符号名与规则编号**，不写行号——行号每次改代码都会失效。

### 容易忽略但很关键的三处「非提示词」约束

- `src/pipeline.js` 的 `shots.slice(0, 6)` — 提示词里写的是「2-5 个画面」，但归一化层最多收 6 个。改数量上限要两边一起改，否则会被静默截断。
- `src/pipeline.js` 的 `sensation` 字段 — 名字改了这里不改，模型输出就会掉进虚空。
- `src/config.js` 的 `PROVIDERS` 数组 — 模型的更换入口。同一份提示词换模型，效果可能天差地别。

## 二、改提示词的正确姿势

**核心原则：固定输入，一次只改一处。**

### 1. 固定一段测试用的梦

自己写一段 100-200 字的梦，存成文件，每次实验都用同一段。否则你分不清是提示词变了还是输入变了。

```bash
# 建议存一份，之后每次都贴它
echo "我梦见在图书馆里，地板是白色的瓷砖..." > /tmp/dream-fixture.txt
```

### 2. 一次只改一处

改完立刻刷新页面重跑，和上一次的结果对比。**同时改三处，你永远不知道是哪一处起了作用。**

### 3. 看什么指标

不要只看「感觉好不好」，盯这三个具体信号：

| 信号 | 好的表现 | 坏的表现 |
|---|---|---|
| **原文忠实度** | 意象都在原文里 | 出现了原文没有的东西 |
| **画面数量** | 等于梦的自然段落数 | 总是 4 个（模型在凑数） |
| **风格锚点** | 每个画面都贴合 | 有一两个画面「跳」出来了 |

### 4. 记录

建一个 `docs/prompt-experiments.md`，一行一条：

```
日期 | 改了什么 | 输入 | 结果 | 结论
10-13 | VISUAL_SYSTEM 规则1 加「边缘溶解」 | 图书馆之梦 | 画面边缘更虚 | 保留
```

## 三、症状 → 该改哪里

拿着症状直接查表。

| 你看到的症状 | 改哪里 | 怎么改 |
|---|---|---|
| 读起来像奇幻短片，不像梦 | `ANALYZE_SYSTEM` 的「梦的运作方式」六条 | 六条是梦境感的全部来源。觉得不够就再加一条，加的是**梦的机制**，不是形容词 |
| 标题像作品名，不像随口说的 | `ANALYZE_SYSTEM` 里 `title` 的注释 | 把「像醒来后随口说出的名字」换成更具体的负面例子，如「不要出现书名号、不要用『之』字」 |
| 画面太「合理」，梦的不合理被抹平 | `VISUAL_SYSTEM` 规则 3 | 这一条是顶住文生图模型合理化倾向的唯一防线。可以补上具体的失败案例 |
| 几个画面风格不统一 | `VISUAL_SYSTEM` 规则 1 的词数 + 规则 5 | 锚点太短不稳定、太长模型会稀释。25-45 词是实测的舒适区 |
| 模型编造了原文没有的意象 | `ANALYZE_SYSTEM` 规则 1 + 末尾的兜底句 | 兜底句（「这是还原方式，不是添加内容的许可」）就是专门防这个的，别删 |
| 画面数量总是 4 个 | `ANALYZE_SYSTEM` 规则 5 | 模型有凑整倾向。把「2-5 个」改成更硬的判断标准，比如「按场景切换的边界来切」 |
| JSON 解析失败 / 输出被截断 | 两段 system 末尾的格式约束 | 先确认是格式问题还是长度问题。长度问题改 `pipeline.js` 的 `slice` 上限或换更长的模型 |
| 每次结果都一个套路 | `pipeline.js` 的 `temperature` | 解析段 `0.85`（求发散），视觉段 `0.6`（求一致）。想让文案更大胆就往上调 0.1，想更稳就往下调 |
| 输出的英文提示词太像诗句 | `VISUAL_SYSTEM` 规则 7 | 已有「逗号分隔的短语，不要写完整句子」。模型偶尔会忘，可以把这条挪到最前面加粗强调 |

## 四、三个最容易犯的错

### 1. 堆「不要」

提示词里每多一条「不要 X」，模型对 X 的关注度反而上升。**能用正向描述就用正向描述。**

- 弱：`不要写得太文艺`
- 强：`只写具体的光线、材质、运动，不写比喻`

### 2. 在 user 消息里堆规则

`analyzeUserPrompt` 只该放「这一次的输入」。任何持续性规则都属于 `system`——放错位置，模型会把它当成一次性的临时要求。

### 3. 改完不验证

没有填 API Key 的情况下，改提示词是**盲改**。先在「模型设置」里填一个 Key（DeepSeek 或智谱可以免费领），再去调。

## 五、可以照抄的三个实验

按顺序做，能快速建立手感。

**实验 A · 验证「梦的运作方式」六条的实际作用**

删掉 `ANALYZE_SYSTEM` 里「梦的运作方式」那一节的六条机制，用同一段梦重跑。对比前后，你会清楚看到这六条承担了多少工作量。

**实验 B · 感受 temperature**

把 `pipeline.js` 里解析段的 `temperature: 0.85` 改成 `0.3`，重跑三次，再改成 `1.2` 重跑三次。低温度下每次结果高度雷同，高温度下会出现意想不到的组合——但也更容易跑偏。

**实验 C · 试探风格锚点的边界**

把 `VISUAL_SYSTEM` 规则 1 的词数改成 `5-15`，看画面是否开始松散；再改成 `60-90`，看模型是否开始忽略一部分描述。这比读任何教程都更能理解锚点长度的意义。

## 六、出图侧的旋钮

文字侧决定画面的**内容**，出图侧决定画面的**质感**。前者占效果的八成——如果你觉得图不对，先怀疑文字侧的提示词，再动这里。

### 旋钮在哪

| # | 位置 | 管什么 |
|---|---|---|
| 1 | `src/prompts.js` → `IMAGE_GUARD` | **正向**约束，拼在每条提示词末尾，所有接口都生效 |
| 2 | `src/prompts.js` → `IMAGE_NEGATIVE` | **负向**约束，只在支持 `negative_prompt` 的接口单独下发 |
| 3 | `src/prompts.js` → `composeImagePrompt` | 正向约束的拼装方式 |
| 4 | `src/config.js` → `PROVIDERS[].image` | 出图模型、支持的尺寸、尺寸字段名、是否支持 negative_prompt |

### 为什么是两个常量，不是一条

因为同一个字符串没法同时当正向和负向用。出图侧有两条硬要求：

- **第一视角**（`first-person view`）——「希望画面里有什么」
- **不出现可辨认的人脸**（`faces kept out of frame or turned away`）——同样是正向写法

如果把这两条塞进一条字符串、再按老办法在硅基流动上丢给 `negative_prompt`，就会变成「**不要**第一视角」——意思正好反了。所以拆成两个常量：

- `IMAGE_GUARD` 走正向提示词，**所有接口都拼**
- `IMAGE_NEGATIVE` 走 `negative_prompt`，**只有 `provider.image.negative` 为 true 的接口才下发**

还有一条**故意不写进 `IMAGE_GUARD`** 的要求：「我」的手、影子、脚步可以入画。它是逐画面的选择（画面记录里提到了才写），而 `IMAGE_GUARD` 拼的是**每一条**提示词——写进去等于要求一整间空旷阅览室也必须伸进一只手。这条落在 `VISUAL_SYSTEM` 规则 5。

还有一条经验：**正向约束里不要写「不要 X」**。提示词里的否定容易反过来抬高模型对 X 的关注度，要排除的东西写进 `IMAGE_NEGATIVE`。

### 最终提示词是怎么拼出来的

```
画面提示词（VISUAL_SYSTEM 生成）
  + 风格锚点（同上，保证跨画面一致）
  + IMAGE_GUARD（正向：第一视角 / 人物处理 / 质感）   ← 所有接口都拼，逐段去重
negative_prompt = IMAGE_NEGATIVE（仅支持该字段的接口）
```

拼装会**按逗号切段去重**：规则 5 要求每条提示词自带 `first-person view`，`IMAGE_GUARD` 里也有这一条，不去重的话同一句话会在最终提示词里出现两次（风格锚点末尾的 `film grain` 同理）。只跳过完全相同的短语，不会误伤 `fine film grain texture` 这类更具体的写法。

### 症状 → 该改哪里

| 你看到的症状 | 改哪里 | 怎么改 |
|---|---|---|
| 画面太干净、像素材库照片 | `IMAGE_GUARD` | 加 `uneven lighting, dust, slight blur` |
| 画面里冒出乱码文字或招牌 | `IMAGE_NEGATIVE` | 确认 `legible text, logos, watermarks` 还在 |
| 每张图人脸都不一样 / 崩坏 | `IMAGE_GUARD` + `IMAGE_NEGATIVE` | 正向保留 `faces kept out of frame or turned away`；负向加 `portrait photography` |
| 出现正脸，或视角跑到第三人称 | `IMAGE_GUARD` | 确认 `first-person view` 还在；再回 `VISUAL_SYSTEM` 规则 4、5 检查文字侧 |
| 想保留「我」的手／影子／脚步，但模型把画面清空了 | **不是出图侧的问题** | 在**该画面的 prompt** 里写 `own hands at the edge of the frame` / `the viewer's own shadow on the steps`；别写进 `IMAGE_GUARD`（它会作用于每一张图，包括空镜） |
| 画面里出现了「我」的全身或镜中倒影 | `IMAGE_NEGATIVE` | 确认 `full-body view of the dreamer`、`mirror reflection of the dreamer` 还在 |
| 明明原文没提，画面却硬塞进一只手 | `VISUAL_SYSTEM` 规则 5 | 那句末尾的「不要凭空虚加」被删了或没生效，补回去 |
| 图太亮太「日光」 | `IMAGE_GUARD` | 加 `underexposed, deep shadows, low key` |
| 几张图风格不统一 | **不是出图侧的问题** | 回到 `VISUAL_SYSTEM` 规则 1 调风格锚点 |
| 报「尺寸不被支持」 | `config.js` 的 `sizePreset` | 该服务商只认列表里的值，别手填别的 |
| 报 400 / 404 / 模型不存在 | 设置面板的「图片模型」 | 先确认模型名，再确认接口地址是同一域名 |
| 免费模型触发限流 | 不用改代码 | 出图本来就是串行的；失败的单张点「重试」即可 |

### 一个刻意的设计

出图是**串行**的（`pipeline.js` 的 `renderDreamImages`），不是并行。免费模型普遍有并发限制，同时发四张的结果往往是四张一起被限流。单张失败也不会中断整批——把成功的留下，失败的单独重试，比全部作废有用。
